# 记忆注入指南（怎么让记忆真正被用上）

**先读这一句**：MemVault 只负责**存取**记忆，它**没有任何自动注入机制**。
MCP 是 pull 模型——服务端只暴露 14 个工具，**是否读、什么时候读、读完怎么用，全部由客户端（也就是模型）决定**。

这不是缺陷，是 MCP 的设计：服务端无法往模型的上下文里塞东西。但结果是——
**如果不在项目里写下「什么时候该召回」，这个库基本不会被用到**。模型没有理由主动去查一个它不知道存在的记忆。

本指南给出四种注入路径，按可靠性排序。

## 四种注入路径

| 路径 | 谁负责 | 可靠性 | 何时用 |
|---|---|---|---|
| ① 项目指令文件（`CLAUDE.md` / `AGENTS.md`）写明召回时机 | 你，客户端侧 | **高** | 默认就该做，成本最低、收益最大 |
| ② 核心记忆块拼进 system prompt | 客户端读取并拼接 | 高（但要自己写拼接代码） | 需要「永不忘」的稳定偏好、身份、约定 |
| ③ 模型自发调 `memory_search` | 模型自己决定 | 低 | 不能作为唯一手段 |
| ④ REST `/api/v1` → 外部应用渲染 | 外部应用（如 project-hub 记忆页） | 不适用 | 注入的是**给人看的 UI**，不是模型上下文 |

## ① 项目指令文件（推荐先做这个）

在项目根放 `CLAUDE.md`（Claude Code）或 `AGENTS.md`（多数其他 harness，DSH 读这个），
内容就是把「什么时候查、什么时候写」讲清楚。

直接复制 [`examples/injection/CLAUDE.md`](../examples/injection/CLAUDE.md) 到你的项目根即可。

要点是**给出触发时机**，而不是泛泛地说「记得用记忆」：

- 「**开工前**：先 `memory_search` 当前任务的关键词（模块名 / 报错信息 / 业务名），再动手。」
- 「**得出稳定结论后**：把结论 `memory_add` 进去；只记稳定事实，不记临时状态。」
- 「**不要记**：一次性的调试输出、能被 git 记录的东西、几分钟后就失效的状态。」

反面例子（模型基本不会照做）：「你有记忆工具，请善用。」——没有时机，等于没说。

## ② 核心记忆块（常驻上下文）

`core_memory_*` 是 Letta 式的 `label + value + value_limit` 常驻块，例如 `persona`（我的偏好）、
`human`（用户是谁）、`project`（本项目约定）。

**MemVault 只存不拼**——架构文档里写的「可作为 system prompt 上下文」是能力描述，
把块拼进 system prompt 是**客户端**的事。两种做法：

1. **写死**：把稳定的块内容直接写进 `CLAUDE.md`，用 `core_memory_*` 当权威副本维护。
   简单，但改了要手动同步。
2. **动态拼**：会话启动时调 `core_memory_get`，把返回值插进 system prompt。
   需要客户端支持（Claude Code 可用 hooks / statusline 之类的机制，或自己包一层）。

块有 `value_limit`（默认 2000 字符），**超限由智能体自己压缩，服务端只做校验和报错**。

## ③ 与 ④ 的边界

- ③ 单独用不可靠：没有指令时模型不会去调。它适合作为 ① 的补充（「刚才那条结论顺手记一下」）。
- ④ 是给人看的。project-hub 的记忆页通过 REST 渲染，**不代表模型也看到了这些记忆**。
  别把「页面上有」当成「模型知道」。

## 作用域：注入的钥匙

记忆按 `user_id` / `agent_id` / `run_id` 三元组隔离，**作用域不同 = 看不见**。
省略时走默认作用域（当前 OS 用户 / 当前项目路径 slug），也可用 `.env` 的
`MEMVAULT_DEFAULT_USER_ID` / `MEMVAULT_DEFAULT_AGENT_ID` / `MEMVAULT_DEFAULT_RUN_ID` 固定。

先调 `memory_whoami` 确认当前进程解析出的默认作用域，再判断「为什么我搜不到刚记的东西」。

**本项目 `.env` 的一个已知取舍**：`MEMVAULT_DEFAULT_AGENT_ID=claude-code-memory` 被钉死了，
好处是所有客户端（Claude Code / DSH / Cursor）共享同一份记忆、不会各建一个空库；
代价是**项目之间不再自动隔离**——A 项目的结论会出现在 B 项目的检索结果里。

需要按项目隔离时，二选一：

- 调用时显式传 `agent_id`（如 `agent_id=my-project`），不要依赖默认值；
- 或把 `.env` 里的 `MEMVAULT_DEFAULT_AGENT_ID` 清空，让它按项目路径自动派生。

单次任务/单条流水线的临时隔离用 `run_id`。

## 维护：收敛与清理

记忆只增不减会拖垮召回质量（同一条被反复改写就散成多条）。两个显式工具收口，**都默认只预览**：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `memory_consolidate` | 合并近重复记忆，每组保留最新（时间同秒则保留更长的）一条 | `threshold`（默认 0.92）、`max_memories`（**规模护栏**，默认 10000）、`dry_run` |
| `memory_purge` | 按时间/类型成批删除 | `older_than_days` / `memory_type`（**至少给一个**）、`dry_run` |

- 要真删必须显式 `dry_run: false`。批量删除的默认不该是「动手」。
- `memory_purge` 不给任何过滤条件会被**拒绝**——那是清空整个作用域，应该显式表达。
- `memory_consolidate` 超过 `max_memories`（默认 1 万行）同样会被**拒绝**：成对扫描是
  O(n²)，约 1 秒/万行，且预览也要付这个开销。库很大时应该按 `agent_id` / `run_id`
  分批收敛，而不是简单把上限调大。
- 建议节奏：先预览 → 看分组/命中是否合理 → 再应用。两者都会写 `DELETE` 历史，
  删错了能从 `memory_history` 看到原文。
- 在给模型的指令里可以写一句「发现明显重复或过期记忆时先报告，不要擅自批量删除」，
  避免它自作主张清理。

## 验证注入是否真的生效

1. `memory_whoami` —— 确认作用域是你以为的那个。
2. 说一句「记住：我偏好 X」→ 用 `memory_get_all` 确认真的写进去了。
3. **新开一个会话**，问一个只有靠记忆才能答的问题 → 如果答对了，注入链路才是通的。
4. 控制台 <http://127.0.0.1:8780/dashboard/> 可以直接看到库里到底有什么。

第 3 步是关键：同会话内模型可能只是从对话历史里「记得」，那不能证明跨会话记忆生效了。
